# Communication véhicules — VDA 5050 2.0.0

## Topics

`<interfaceName>/v2/<manufacturer>/<serialNumber>/<topic>` avec `interfaceName` = `uagv`
(configurable `FM_VDA_INTERFACE`). Topics : `order`, `instantActions` (FM → AGV) ;
`state`, `visualization`, `connection` (retenu, last will), `factsheet` (AGV → FM).

## Contenu exploité

AGV → FM (`state`) : position et orientation (`agvPosition`), `localizationScore`,
`positionInitialized`, `velocity`, `driving`, `paused`, `newBaseRequest`, `operatingMode`,
`orderId` / `orderUpdateId` / `lastNodeId` / `lastNodeSequenceId`, `nodeStates` / `edgeStates`,
`actionStates`, `batteryState` (charge, tension, santé, en charge), `loads` (charge mesurée),
`errors` (niveau WARNING/FATAL), `safetyState` (eStop, fieldViolation), `information`.

FM → AGV : ordres (nœuds avec position, orientation GLOBAL par arête, vitesse max, actions
`pick`/`drop`/`waitForTrigger`/`startCharging`), mises à jour d'ordre (extension de la base),
instant actions `startPause`, `stopPause`, `cancelOrder`, `startCharging`, `stopCharging`,
`stateRequest`, `factsheetRequest`, `initPosition`.

## Base et horizon

Les nœuds dont l'index de route est ≤ dernier segment réservé sont `released: true` (base) ;
les suivants sont envoyés non libérés (horizon) pour permettre la planification embarquée.
`sequenceId = 2 × index de route` pour les nœuds, `2 × index + 1` pour les arêtes : une mise
à jour d'ordre (même `orderId`, `orderUpdateId` + 1) recommence au dernier nœud de la base
précédente avec le même `sequenceId`, conformément à la section 6.6 de la spécification.
Un nouvel itinéraire (replanification) est un nouvel `orderId` émis uniquement quand l'AGV
est à l'arrêt sur son dernier nœud.

## Robustesse

- Validation des messages contre les règles structurelles (version 2.x, énumérations, séquence
  nœuds/arêtes, base avant horizon) ; messages invalides comptés et journalisés.
- Contrôle de séquence par `headerId` (doublons et messages anciens ignorés, redémarrage
  d'AGV toléré).
- Heartbeat : silence > `FM_COMMS_TIMEOUT` (5 s) ⇒ `connectionBroken`, alarme `COMMS_LOST`,
  mission suspendue, réservations incertaines. Reconnexion automatique (Paho) et reprise de
  mission (ordre renvoyé).
- Véhicules inconnus vus sur le bus : listés dans `GET /system/info` (`discoveredVehicles`)
  pour faciliter l'enregistrement.
- Authentification MQTT : utilisateur/mot de passe du broker embarqué (`FM_MQTT_USERNAME`),
  TLS possible via un broker externe (`FM_MQTT_URL=ssl://…`).
- Versions : seule la version majeure 2 est acceptée ; les messages sont marqués `2.0.0`.

## Comportement en perte de communication

Le comportement de l'AGV est défini par son contrôleur embarqué (analyse de risques). Le Fleet
Manager cesse d'attribuer des missions, protège les ressources (`uncertain`) et conserve la
mission affectée. Après `ReassignAfter` (2 min), une mission **sans charge à bord** est remise
en file ; une mission dont la charge peut être à bord est suspendue avec l'indicateur
`loadOnBoardUnverified` et une alarme `LOAD_UNVERIFIED` : la réaffectation exige alors une
confirmation humaine (`POST /missions/{id}/reassign` avec `confirmLoadState: true`).

## Adaptateurs propriétaires

`gateway.Adapter` (SendOrder / SendInstantActions) est le contrat à implémenter pour un
protocole constructeur ; le Fleet Core ne dépend que de ce contrat et des états `core.VehicleState`.
